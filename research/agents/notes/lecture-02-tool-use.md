## 先抓住整堂课

语言模型本身是在生成文字。所谓“使用工具”，是让它按约定格式提出调用请求，由外部程序执行，再把结果交还给模型。要做好这件事，既要设计工具接口，也要处理参数格式、权限、调用顺序、失败和评估。

## 第 1–12 页：工具是什么

- **第 1–2 页｜主题与基本思路。** 本课讲语言模型 Agent 如何使用工具。第 2 页是章节过渡。
- **第 3 页｜工具定义。** 工具是模型调用外部程序的接口，例如搜索、计算器、浏览器、Python 或应用 API。**意思：**模型提出“调用什么、传什么参数”；外部软件决定是否以及怎样执行。
- **第 4 页｜两种收益。** 工具能让模型取得自身参数里没有的信息或能力，也能把计算等工作交给更可靠的程序。**意思：**工具既扩展能力，也改善执行质量。
- **第 5 页｜何时使用。** 查最新信息用搜索，精确计算用代码，读取账户数据用授权 API，改变外部环境用浏览器或 API。**意思：**一次调用也有时间、费用、失败和风险成本，收益应超过这些成本。
- **第 6 页｜示例章节页。**
- **第 7 页｜从能力设计接口。** 先想 Agent 要完成什么，再为每类交互定义范围明确的调用。**意思：**工具设计应服务于具体任务。
- **第 8 页｜`finish(text)`。** 返回最终文字并结束循环。**意思：**这是控制 Agent 流程的动作，不是访问外部程序的工具。
- **第 9 页｜`search_web(query)`。** 搜索返回资料，模型再据此回答“今天宣布了什么”。**意思：**需要最新事实时，回答应建立在检索结果上。
- **第 10 页｜`execute_code(code)`。** 执行求平均数的代码，得到 34。**意思：**可交给程序做确定性的运算。
- **第 11 页｜`generate_image(query)`。** 把文字描述交给图像生成工具。**意思：**工具结果也可以是图片，而非一段文字。
- **第 12 页｜自定义函数。** `create_grocery_cart(items)` 创建购物车并返回商品数、价格。**意思：**应用可以把自己的业务能力包装成一个有明确参数的调用。

## 第 13–17 页：把代码当作工具

- **第 13 页｜章节页：程序化工具调用。**
- **第 14 页｜代码是“组合工具”。** 一段代码能使用变量、循环和库，串起多次操作。**意思：**复杂流程不一定要让模型逐步发出大量单独调用。
- **第 15 页｜CodeAct 对比示例。** 比较逐次发出文字或 JSON 调用，与写一段代码计算各国购买手机的最终价格。**意思：**代码能在一次执行中处理循环、数据流和取最小值，因此可减少交互轮次。
- **第 16 页｜CodeAct 结果。** 幻灯片展示的 8 个模型中，代码方式的成功率都最高；其中 7 个模型使用的交互轮次最少。放到研究中的全部 17 个模型，两项计数都是 12/17。**意思：**这是所展示实验范围内的结果，不能直接理解为“任何任务写代码都最好”。
- **第 17 页｜代码的代价。** 代码表达力强，也更难限制，可能访问文件、网络和进程。**意思：**给 Agent 代码执行权时，要配套沙箱、资源限制、权限与审计记录。

## 第 18–25 页：一次工具调用怎样走完

- **第 18 页｜章节页：工具机制。**
- **第 19 页｜工具调用也是模型输出。** 模型可以继续输出普通文字，也可以输出特定格式的调用请求。**意思：**真正执行调用的是外围程序，课件称它为 *harness*，可理解为管理 Agent 运行的程序。
- **第 20 页｜消息如何进入模型。** API 中分开的 system、user、assistant 消息，会经 *chat template*（聊天模板）序列化成模型输入。**意思：**消息的“角色”最终也要转成模型可读取的序列。
- **第 21 页｜请求中附上工具定义。** `get_weather` 的定义写明名称、参数类型和必填的 `city`。**意思：**模型要知道有哪些工具，以及每个工具接受什么输入。
- **第 22 页｜定义进去，调用出来。** 模型输出 `get_weather` 及 `city=Pittsburgh`；API 响应给这次调用配上唯一 ID。**意思：**模型生成调用内容，外围系统负责记录和跟踪调用。
- **第 23 页｜模型协议各异。** Qwen、Mistral、DeepSeek 用不同标记表示工具调用。**意思：**同一个工具接口，到了不同模型那里仍需相应的编码与解析。
- **第 24 页｜OpenHands 如何派发。** 先注册工具；调用时解析名称和参数，查找工具、校验参数、执行，最后返回观察结果。**意思：**“模型说要调用”到“程序真的执行”之间有一条明确的处理链。
- **第 25 页｜用调用 ID 对上结果。** 返回消息的 `tool_call_id` 指向原调用。**意思：**尤其有多个调用时，系统必须知道哪个结果属于哪个请求。

## 第 26–35 页：怎样保证调用格式正确

- **第 26 页｜章节页：受约束生成。**
- **第 27 页｜格式错误的调用。** 示例 JSON 少了右花括号，外围程序无法解析。**意思：**模型即使选对工具，也可能因为输出格式错误而无法执行。
- **第 28 页｜四层格式约束。** 检查 JSON 语法、字段结构、字段类型和允许的取值。**意思：**这些约束保证“长得合法”，不能保证事实正确、权限足够、工具选得对或任务完成。
- **第 29 页｜JSON Schema。** 用机器可读的规则规定 `city` 是字符串、`units` 只能是 `C` 或 `F` 等。**意思：**工具参数可以自动校验。
- **第 30 页｜合法与不合法。** `units:"F"` 符合示例规则，`units:"K"` 虽是合法 JSON，却不符合该规则。**意思：**“能解析为 JSON”和“满足工具参数要求”是两道检查。
- **第 31 页｜下推自动机。** 它用当前状态记录语法位置，用栈记住嵌套结构。**意思：**生成对象、数组等层层嵌套的内容时，需要记住还欠哪些结束符。
- **第 32 页｜检查要深入到字节。** 一个模型 token 可能横跨多个语法片段，也可能只覆盖片段的一部分。**意思：**不能简单地把 token 边界当成 JSON 语法边界。
- **第 33 页｜缓存允许的 token。** 先处理已有前缀，复用可缓存的判断，只对少量依赖具体上下文的候选 token 做完整检查。**意思：**约束生成也要考虑速度，避免每一步都从头检查全部候选。
- **第 34 页｜Token masking。** 把当前语法不允许的候选 token 概率压为零，再从剩余候选中采样。**意思：**模型仍在生成，但系统拦住了此刻会破坏格式的选项。
- **第 35 页｜加速来源。** 图中展示缓存处理多数 token、持久化栈处理分支，以及 CPU 检查与 GPU 推理重叠。**意思：**格式约束的实际价值还取决于执行开销。

## 第 36–46 页：REST API 与 MCP

- **第 36 页｜章节页：REST API 调用。**
- **第 37 页｜库函数。** Python 的 `get_weather(city, units)` 可供同一进程内的代码调用。**意思：**有函数接口，不等于远程 Agent 已能通过网络调用它；还需要地址、协议、数据格式和身份验证。
- **第 38 页｜REST API。** FastAPI 把天气函数放到 HTTP 的 `/weather` 地址，并要求 API Key。**意思：**其他程序可以通过网络请求这个功能。
- **第 39 页｜OpenAPI 描述。** 文档写明 HTTP 路径、参数、取值及认证方式。**意思：**客户端可以机器化地了解“怎么请求这个 API”。
- **第 40 页｜Agent 通过 `curl` 请求。** 先读 API 描述，再拼请求；Shell 从环境变量取得密钥。**意思：**这样做直接，但能运行 Shell 的 Agent 也可能接触到该密钥。
- **第 41 页｜章节页：MCP。**
- **第 42 页｜MCP 的连接结构。** AI 应用作为 host，通过 client 连接本地或远程 server。**意思：**MCP 是面向 Agent 暴露能力的一种接口；调用 REST API 并不一定需要它。
- **第 43 页｜由 OpenAPI 转成 MCP 工具。** 示例把 `GET /weather` 映射为 `get_weather(city, units)`。**意思：**已有 Web API 可以进一步包装成 Agent 可发现的工具。
- **第 44 页｜两套凭证。** 上游 API Key 用于调用天气服务；MCP API Key 用于保护 MCP 入口。**意思：**两段访问分别授权。课件也说明静态令牌适合教学或开发，正式部署应采用更合适的认证机制。
- **第 45 页｜凭证代理。** Agent 连接 MCP server，server 再用另一套凭证访问天气 API；模型无需看到两边的密钥。**意思：**中间层可以控制访问并隔离上游凭证。
- **第 46 页｜两种接口的关系。** OpenAPI 描述 HTTP 操作；MCP 规定 AI 应用如何发现和调用能力，还支持资源、提示等内容。**意思：**它们可共享结构化参数描述，但解决的问题和调用约定不同。

## 第 47–57 页：并行调用与评估

- **第 47 页｜章节页：组织多个调用。**
- **第 48 页｜串行耗时。** 模型生成与天气、日历、航班查询依次等待，示例合计约 **6.4 秒**。**意思：**每多等一次模型或工具，整体响应就更慢。
- **第 49 页｜并行耗时。** 三个独立查询同时执行，示例约 **2.8 秒**：两次模型生成时间，加上最慢工具的时间。**意思：**独立任务并行时，等待时间主要取决于最慢的一个。
- **第 50 页｜并行的前提。** 天气、日历、航班状态可独立查询；先找客户 ID、再查订单、最后退款必须按顺序。**意思：**有数据依赖或相互影响的操作不能随意并行。
- **第 51 页｜并发代码。** `asyncio.gather` 同时执行调用，并返回各自的 `call_id` 与结果。**意思：**结果完成顺序可能不同，仍须正确配对，也须处理单个调用失败。
- **第 52 页｜章节页：评估工具使用。**
- **第 53 页｜Berkeley Function Calling Leaderboard。** 测单轮、多轮、Agent 场景和鲁棒性。**意思：**工具能力不只是一道“函数参数填空题”。
- **第 54 页｜评估整个过程。** 分别检查工具选得对不对、参数对不对、调用顺序对不对、最终目标是否达成。**意思：**参数格式正确，也可能得到一个看似合理却错误的最终答案。
- **第 55 页｜实际运行质量。** 还要看耗时、调用量、费用、超时、重试、权限和副作用。**意思：**答对一次不代表系统在真实环境中好用。
- **第 56 页｜故障来源。** 模型可能选错工具或忽略结果；外围程序可能解析、认证、配对出错；服务方可能超时、限流或执行失败。**意思：**排查时要定位是哪一层出了问题。
- **第 57 页｜服务商错误率图。** 课件引用一张标注为 **2026 年 8 月 27 日** 的服务商工具调用错误率快照。**意思：**真实服务的失败率会因服务商和时间而异；这页适合用来理解“运营指标也要测”，不宜把图中数字当成今天的现状。

## 第 58–60 页：收束

- **第 59 页｜五层框架。** 课件把工具使用归为能力、调用机制、格式约束、REST/MCP 接口、编排与评估。**意思：**一个能用工具的 Agent，是这些层共同工作的结果。
