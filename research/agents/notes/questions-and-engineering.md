# 从学习问题到工程判断

这里保留本轮讨论的真实问题，并将回答改写成可继续验证的判断。用户问题来自当天讨论；解释和跨材料连接为 AI 辅助整理，不能当作用户已独立证明的结论。

## 1. 任务只有少量上下文，为什么软件仍然复杂？

**用户问题：**回复任务看起来只需提示词，没有复杂规划，为什么做成应用、迁移到 Mac 后会有很多问题？

**讨论结论：**生成一段回复只占一小部分。数据接入、消息身份、去重、处理状态、重启恢复、桌面权限、依赖打包和操作系统适配都可能独立失败。更强的模型不能自动补齐缺失依赖或不兼容的平台接口。

| 看起来的一步 | 实际要确认的事 | 可观察的验收 |
| --- | --- | --- |
| 收到消息 | 来源、发送者、时间、唯一标识是否正确 | 合成消息与读取结果逐字段比对 |
| 生成草稿 | 规则与背景是否匹配，有无遗漏限制 | 用固定例子检查回复及引用依据 |
| 持续工作 | 重复扫描、断线、重启后状态是否一致 | 同一消息重放三次只产生一个待办 |
| 迁移平台 | 系统接口和依赖是否实际存在 | 在目标设备独立验证最小数据入口 |

**整理推论：**开发顺序应先验证最大的外部未知，再建设依赖它的体验。模拟能验证业务逻辑，目标设备实测才能证明平台接入。这里没有发布或读取私人消息，也没有据此宣称 Mac 适配完成。

## 2. 依赖注入和控制反转，要不要重新系统学？

**用户问题：**AI 会不会乱套设计模式？是否需要重新学一遍？

先掌握能审查设计的几个判断。依赖注入，就是把需要的工具从外部传入；控制反转，是将某部分选择或执行控制交给外部。依赖注入是后者的一种常见做法。

```python
class ReplyWorkflow:
    def __init__(self, reader, drafter):
        self.reader = reader
        self.drafter = drafter

    def preview(self):
        return [self.drafter.draft(m) for m in self.reader.read()]
```

这是未接外部服务的结构示例。实际读取器、模拟读取器遵循同一个 `read()` 约定，后续流程才能换实现。它没有实现持久化、去重或恢复，不能作为完整应用。

**与第四课的连接（整理推论）：**统一的上层技能接口配不同环境实现，与业务流程接受不同读取器有相似思路。但两者不因此成为同一概念：一个讨论经验与动作复用，一个讨论软件依赖关系。

审查 AI 代码时问：这里为什么自己创建依赖？测试能否换成替身？新抽象解决了哪一个已发生的问题？若回答不清楚，增加设计模式的层数没有帮助。

## 3. 项目文件多，是否就一定占满上下文？

概念上要分开“磁盘上的资料”和“某次模型请求里实际送入的资料”。文件数量本身不是输入长度；反复读入长日志和过期资料，才会直接扩大当前输入。具体产品怎样选择和压缩材料取决于其实现，本资料不把课堂模型当成任何产品的内部机制说明。

可采用的工程做法：保留简短状态、当前约束、已验证事实和来源；需要细节时回查。摘要后能否继续正确完成任务，比摘要短了多少更值得测。
